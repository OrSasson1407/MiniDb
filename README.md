# MiniDb

מנוע מסד נתונים קטן ב-C#, נבנה מאפס כפרויקט לימודי. תכנון מלא: [docs/superpowers/specs/2026-10-20-minidb-design.md](docs/superpowers/specs/2026-10-20-minidb-design.md). תוכנית המימוש: [docs/superpowers/plans/2026-10-20-minidb.md](docs/superpowers/plans/2026-10-20-minidb.md).

## מה יש בפנים

- **Storage**: קובץ דפים של 4 KB עם CRC-32 בסוף כל דף, ו-buffer pool (LRU) בגודל קבוע. עמודים שהשתנו בטרנזקציה נשארים בבריכה עד פינוי או checkpoint.
- **Database**: דף כותרת עם magic `MINIDB01`, ובדיקת שלמות בפתיחה.
- **Records**: סריאליזציה של שורות (Int32, Int64, Double, Bool, String ב-UTF-8). עמודות ברוחב קבוע באות ראשונות, כך שכל אחת נקראת ממיקום ידוע. ה-API מחזיר `RowView` שמפענח עמודה רק לפי דרישה.
- **Catalog**: הגדרות טבלאות, נשמרות בדפים עצמם, עם מטמון בזיכרון.
- **Index**: B+ tree על מפתח ראשי `Int64` (טבלה מקובצת: השורות בתוך העלים), ואינדקסים משניים על עמודות `INT`/`BIGINT` דרך `CREATE INDEX ON טבלה (עמודה)`.
- **Transactions**: WAL שרושם רק את הבתים ששונו בדפים (page delta), commit עם fsync (אפשר לכבות), checkpoint, והתאוששות מקריסה (טרנזקציות ללא commit מתעלמות, וקרע בסוף היומן נחתך).
- **API**: `MiniDatabase`, `Table`, `RowView` בקוד C#.
- **SQL**: `CREATE TABLE`, `INSERT`, `SELECT ... WHERE ... LIMIT`, `DELETE ... WHERE`, עם planner שבוחר בין חיפוש נקודתי, סריקת טווח ב-B+ tree, וסריקה מלאה. סינון נעשה על `RowView`, כך שכל השוואה קוראת רק את העמודה שבתנאי.

## הרצה

```bash
dotnet run --project src/MiniDb.Cli -- shop.mdb
```

```sql
CREATE TABLE users (id BIGINT PRIMARY KEY, name VARCHAR(50))
INSERT INTO users VALUES (1, 'שלום')
SELECT * FROM users WHERE id >= 1 LIMIT 10
DELETE FROM users WHERE id = 1
```

## בדיקות

```bash
dotnet test tests/MiniDb.Tests
```

108 בדיקות: שכבה לשכבה, כולל בדיקת fuzz של ה-B+ tree מול `SortedDictionary`, בדיקות התאוששות מקריסה ו-torn tail, בדיקות checksum, ובדיקות SQL מקצה לקצה.

## השוואה למסדי נתונים אחרים

הריצה האחרונה: BenchmarkDotNet, Release, Windows 11, .NET 8, מכונה אחת. כל המנועים על אותם נתונים (`id BIGINT`, `name` מחרוזת, `score INT` עם ערך 7 בכ-10% מהשורות), ואינדקס על `score` בכל מנוע לעומסי הקריאה. MiniDb בהגדרות ברירת המחדל (מאגר של 4,096 דפים, 16 MB). SQLite במצב WAL עם `synchronous=FULL`. LiteDB בהגדרות ברירת המחדל (durability לא נבדק). MongoDB על localhost, `w:1, journal:true`. PostgreSQL לא נכלל (דורש סיסמה).

| עומס | MiniDb | SQLite | LiteDB | MongoDB |
|---|---|---|---|---|
| הכנסה batch, 10k בטרנזקציה אחת | 31.9 ms | **19.3 ms** | 176 ms | 70.7 ms |
| autocommit, 1k טרנזקציות נפרדות | 488 ms | **444 ms** | 90.7 ms* | 735 ms |
| חיפוש נקודתי, 100k (לכל קריאה) | **0.48 µs** | 1.14 µs | 19.3 µs | 156 µs |
| סריקה מלאה, 100k | **3.6 ms** | 10.7 ms | 67 ms | 133 ms |
| סריקה מסוננת (`score = 7`), 100k | 6.8 ms (SQL) | **4.3 ms** | 9.1 ms | 27.4 ms |

\* LiteDB ככל הנראה לא מבצע fsync לכל commit; לא נבדק.

**מקביליות (חיפושים נקודתיים, 20,000 לכל חוט, 100k שורות):** 1 חוט 14.1 ms, 2 חוטים 25.3 ms, 4 חוטים 57.9 ms, 8 חוטים 164 ms. התפוקה לא גדלה עם מספר החוטים: נעילת הקריאה ו-GC נשארו צוואר בקבוק.

### איך לקרוא את הטבלאות

- MiniDb מהיר בקריאה (חיפוש נקודתי וסריקה מלאה). היתרון אמיתי אבל צר: המנוע רץ בתוך התהליך, בלי SQL ובלי רשת.
- SQLite מהיר יותר בהכנסה batch ובסריקה מסוננת דרך אינדקס.
- MiniDb לא שווה ביכולות לאף אחד מהמנועים: אין JOIN, ORDER BY, UPDATE, אינדקסים על מחרוזות, MVCC, ופרוטוקול רשת.
- הטבלאות נמדדו על מכונה אחת, עם סטיות גבוהות בחלק מהשורות.

### שלבי האופטימיזציה

| שלב | מה נעשה | מה נמדד |
|---|---|---|
| 1. מאגר דפים | ברירת מחדל 16 MB, סריקה לא מוציאה דפים חמים, קריאה מראש | חיפוש 10.7 → 0.32 µs; סריקה 6.3 → 1.9 ms |
| 2. נתיב commit | רישום רק של הבתים ששונו בדף (page delta) | autocommit 425 → 363 ms; הקצאות 17.4 → 1.3 MB |
| 4. טבלה מקובצת | השורות בתוך עלי העץ | סריקה נשארה 2.2 ms; חיפוש דרך אינדקס משני איטי יותר (4.0 → 5.9 ms) |
| 3. אינדקסים משניים | `CREATE INDEX` על עמודות שלמות, נשמר בקטלוג ומתוחזק בהכנסה ובמחיקה | סינון SQL עם אינדקס 8.4 → 4.0 ms (ב-10% מהשורות) |
| 5. מקביליות | קוראים במקביל, כותב אחד בבלעדיות, מאגר מחולק ל-partitions | חיפוש בודד 317 → 480 ns; 8 חוטים 362 → 164 ms |

**מה לא הושג:** שלב 5 לא נותן תפוקת קריאה ליניארית במספר הליבות. שלב 3 מועיל בעיקר בסלקטיביות גבוהה: בעומס כאן (10% מהשורות) הוא מחזיר הרבה שורות. שלב 4 הוריד את ההקצאות בסריקה לרמה של שלב 3, אבל איבד מעט מהמהירות בשאילתות דרך אינדקס.

**מגבלות של המקביליות:** קוראים מחכים לכותב (אין MVCC), טרנזקציה מפורשת נועלת את המסד לכל שאר החוטים עד לסיומה, ואין לכתוב בזמן לולאה שקוראת `Scan` על אותו חוט.

## מבנה

```
src/MiniDb.Core/                המנוע: Storage, Database, Records, Catalog, Index, Transactions, Query, Api
src/MiniDb.Cli/                 מעטפת SQL אינטראקטיבית
tests/MiniDb.Tests/             בדיקות יחידה, התאוששות ו-SQL
benchmarks/MiniDb.Benchmarks/   מדידות מול SQLite, LiteDB ו-MongoDB
```

השכבות תלויות רק כלפי מטה: `Api → Query → Index/Transactions → Storage`.

## מגבלות ידועות

- אינדקסים משניים לא ממומשים (המפרט מגדיר אותם כאופציונלי). WHERE על עמודה שאינה המפתח הראשי הוא סריקה מלאה.
- מחיקה משאירה חורים בדפי הנתונים; אין compaction או VACUUM.
- כותב אחד בכל רגע; קוראים מחכים לכותב (אין MVCC או snapshots). התפוקה במספר חוטים לא ליניארית.
- טרנזקציה חייבת להיכנס ל-buffer pool כולו (no-steal), ולכן ברירת המחדל של 256 דפים מגבילה את גודל הטרנזקציה.
- AllocatePage אינו טרנזקציוני: דפים שהוקצו בטרנזקציה שבוטלה נשארים מוקצים כאפסים.
- `FsyncOnCommit=false` מאיץ commits, אבל אחרי הפסקת חשמל ייתכן שיאבדו ה-commits האחרונים. הקובץ נשאר עקבי, כי היומן נכתב לדיסק לפני כל דף.
