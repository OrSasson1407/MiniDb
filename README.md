# MiniDb

מנוע מסד נתונים קטן ב-C#, נבנה מאפס כפרויקט לימודי. מה כלול בגרסה 1.0 ומה לא: [docs/v1-scope.md](docs/v1-scope.md). שינויים: [CHANGELOG.md](CHANGELOG.md). תכנון מלא: [docs/superpowers/specs/2026-10-20-minidb-design.md](docs/superpowers/specs/2026-10-20-minidb-design.md). תוכנית המימוש: [docs/superpowers/plans/2026-10-20-minidb.md](docs/superpowers/plans/2026-10-20-minidb.md).

## מה יש בפנים

- **Storage**: קובץ דפים של 4 KB עם CRC-32 בסוף כל דף, ו-buffer pool (LRU) בגודל קבוע. עמודים שהשתנו בטרנזקציה נשארים בבריכה עד פינוי או checkpoint.
- **Database**: דף כותרת עם magic `MINIDB01`, ובדיקת שלמות בפתיחה.
- **Records**: סריאליזציה של שורות (Int32, Int64, Double, Bool, String ב-UTF-8). עמודות ברוחב קבוע באות ראשונות, כך שכל אחת נקראת ממיקום ידוע. ה-API מחזיר `RowView` שמפענח עמודה רק לפי דרישה.
- **Catalog**: הגדרות טבלאות, נשמרות בדפים עצמם, עם מטמון בזיכרון.
- **Index**: B+ tree על מפתח ראשי `Int64` (טבלה מקובצת: השורות בתוך העלים), ואינדקסים משניים על עמודות `INT`, `BIGINT` ו-`VARCHAR` דרך `CREATE INDEX ON טבלה (עמודה)`. אינדקס מחרוזות שומר את 4 התווים הראשונים, ולכן כל שורה שנמצאה נבדקת שוב במלואה.
- **Transactions**: WAL שרושם רק את הבתים ששונו בדפים (page delta), commit עם fsync (אפשר לכבות), checkpoint, והתאוששות מקריסה (טרנזקציות ללא commit מתעלמות, וקרע בסוף היומן נחתך).
- **API**: `MiniDatabase`, `Table`, `RowView` בקוד C#.
- **SQL**: `CREATE TABLE`, `CREATE INDEX`, `INSERT`, `SELECT`, `UPDATE`, `DELETE`. ב-`SELECT`: `WHERE` עם `AND`/`OR` וסוגריים, `INNER JOIN` (אחד או יותר), `GROUP BY` עם `COUNT`, `SUM`, `MIN`, `MAX`, `AVG`, `ORDER BY` עם `ASC`/`DESC` (ועם `LIMIT` שמחזיק רק את השורות הראשונות בערימה), ו-`LIMIT`.
- **Planner**: בוחר את הגישה הזולה ביותר מבין התנאים שחייבים להתקיים (חיפוש נקודתי, טווח מפתח, טווח אינדקס, או סריקה). טווח אינדקס שמחזיר יותר מ-1,024 שורות מוותר לסריקה מלאה. סינון נעשה על `RowView`, כך שכל השוואה קוראת רק את העמודה שבתנאי. ORDER BY מדלג על מיון כש-B+ tree כבר מחזיר את השורות בסדר הנכון.

## הרצה

```bash
dotnet run --project src/MiniDb.Cli -- shop.mdb
```

```sql
CREATE TABLE users (id BIGINT PRIMARY KEY, name VARCHAR(50))
INSERT INTO users VALUES (1, 'שלום')
SELECT * FROM users WHERE id >= 1 LIMIT 10
SELECT name, COUNT(*) FROM users GROUP BY name ORDER BY name DESC
UPDATE users SET name = 'דנה' WHERE id = 1 OR (id > 10 AND id < 20)
SELECT users.name, orders.total FROM users JOIN orders ON users.id = orders.user_id
DELETE FROM users WHERE id = 1
```

dotnet test tests/MiniDb.Tests

## השוואה למסדי נתונים אחרים

הריצה האחרונה: BenchmarkDotNet, Release, Windows 11, .NET 8, מחשב נייד (i7-1255U: 2 ליבות ביצועים ו-8 חסכוניות), מכונה אחת. כל המנועים על אותם נתונים (`id BIGINT`, `name` מחרוזת, `score INT` עם ערכים 0..999, כך ש-`score = 7` מתאים ל-0.1% מהשורות), ואינדקס על `score` לעומסי הסינון. MiniDb בהגדרות ברירת המחדל (מאגר של 4,096 דפים, 16 MB). SQLite במצב WAL עם `synchronous=FULL`. LiteDB בהגדרות ברירת המחדל. MongoDB על localhost עם `w:1, journal:true`. PostgreSQL לא נכלל (דורש סיסמה).

| עומס | MiniDb | SQLite | LiteDB | MongoDB |
|---|---|---|---|---|
| חיפוש נקודתי לפי מפתח, 100k שורות | **332 ns** | 2.67 µs | 17.8 µs | 211 µs |
| סריקה מלאה, 100k שורות | **4.7 ms** | 11.3 ms | 72.8 ms | 161 ms |
| סינון עם אינדקס (`score = 7`, 0.1%) | **9.2 µs** | 35.9 µs | 118 µs | 708 µs |
| הכנסה batch, 10k שורות בטרנזקציה אחת | 27.2 ms (±19) | 28.1 ms | 45.3 ms | 43.3 ms |
| autocommit, 1,000 טרנזקציות | 387 ms | 422 ms | **101 ms*** | 1,373 ms |

\* LiteDB מבצע commit ב-~100 µs, הרבה מתחת לזמן ה-fsync של המכונה הזו (~400 µs), ולכן כנראה אינו מסנכרן לדיסק בכל commit. לא אומת.

**הכנסה batch:** הערך של MiniDb בטבלה רועש מאוד (סטיית תקן 10 ms). כשמריצים אותו לבד מול SQLite, בלי שאר המנועים בתהליך ועם חימום JIT מלא, התוצאה היא MiniDb 14.0 ms מול SQLite 23.6 ms. בהרצה הקצרה של BenchmarkDotNet חלק גדול מהזמן הוא קוד שעוד לא עבר אופטימיזציה של ה-JIT. מסקנה זהירה: שווה ל-SQLite, לא איטי ממנו.

**נתיב קריאה עם אינדקס, שלושה סלקטיביות** (100k שורות, אותה שאילתה עם ובלי אינדקס על `score`):

| תנאי | התאמות | בלי אינדקס | עם אינדקס |
|---|---|---|---|
| `score = 7` | 0.1% | 4.69 ms | **47 µs** (פי 99) |
| `score < 5` | 0.5% | 7.26 ms | **192 µs** (פי 38) |
| `score < 500` | 50% | 35.9 ms | 31.1 ms (המתכנן מתעלם מהאינדקס) |

כשהאינדקס היה מחזיר יותר מ-1,024 התאמות, המתכנן עובר לסריקה מלאה, כדי שאינדקס לא יאט שאילתה לא סלקטיבית.

**מקביליות (חיפושים נקודתיים מ-Table.Get, 100k לכל חוט):**

| חוטים | תפוקה ב-BenchmarkDotNet | תפוקה בתוכנית מדידה נפרדת |
|---|---|---|
| 1 | 2.5 מיליון לשנייה | 1.7 מיליון לשנייה |
| 2 | 3.5 מיליון | 2.8 מיליון |
| 4 | 4.1 מיליון | 5.7 מיליון |
| 8 | 4.7 מיליון | 9.0 מיליון |

לפני התיקונים הסופיים התפוקה הייתה שטוחה (~2.0 מיליון לשנייה מחוט אחד ועד 8). שני התיקונים: דפים דביקים לשורש ולרמות העליונות של העץ (נעילת LRU וספירת pin אטומית על אותם דפים הפסיקו להיות צוואר בקבוק), ונעילת קריאה מפוזרת במקום `ReaderWriterLockSlim`. בתוכנית המדידה הנפרדת ההרחבה היא פי 5.3 ב-8 חוטים, וב-BenchmarkDotNet פי 1.9. הפער בין השתיים לא הוסבר עד הסוף. שתי הסברות: המעבד הוא חלק מובייל של 15W עם 2 ליבות ביצועים בלבד, ולכן הגג התיאורטי הוא בערך פי 6 ולא פי 8; והריצה הארוכה של BenchmarkDotNet מגבילה הספק. הסטיות בטבלאות הן גדולות כי המכונה לא הייתה ריקה.

### איך לקרוא את הטבלאות

- MiniDb מוביל בקריאה (חיפוש נקודתי, סריקה, סינון דרך אינדקס). היתרון אמיתי אבל חלקו נובע מכך שהמנוע רץ בתוך התהליך, בלי רשת ובלי שכבת ADO.NET.
- בהכנסה batch ובאוטוקומיט MiniDb דומה ל-SQLite, כי שניהם נחסמים על כתיבה ו-fsync.
- MiniDb לא שווה ביכולות לאף אחד מהמנועים: אין JOIN, ORDER BY, UPDATE, אינדקסים על מחרוזות, MVCC, ופרוטוקול רשת.
- כל המספרים ממכונה אחת. אין להשוות אותם למספרים ממכונה אחרת, ובטבלה יש טווחי שגיאה רחבים כי חלק מהריצות התנהלו כשהמחשב עסוק.

### שלבי האופטימיזציה

| שלב | מה נעשה | תוצאה |
|---|---|---|
| 1. מאגר דפים | 16 MB, סריקה לא מוציאה דפים חמים, קריאה מראש | חיפוש 10.7 → 0.32 µs; סריקה 6.3 → 1.9 ms |
| 2. נתיב commit | רישום רק של הבתים ששונו (page delta) | autocommit 425 → 363 ms; הקצאות 17.4 → 1.3 MB |
| 3. אינדקסים משניים | `CREATE INDEX` על עמודות שלמות | סינון SQL 8.4 → 4.0 ms (ב-10% מהשורות) |
| 4. טבלה מקובצת | השורות בתוך עלי העץ | סריקה נשארה 2.2 ms; חיפוש דרך אינדקס איטי יותר |
| 5. מקביליות | קוראים במקביל, כותב אחד | 8 חוטים 362 → 164 ms |
| 6. תיקונים אחרונים | אינדקס-בלבד, בדיקת סלקטיביות, פגיעות מטמון ללא נעילה | סינון סלקטיבי 72.8 → 8.3 µs |
| 7. סבב אחרון | `PinnedPage` כ-struct, דפים דביקים, נעילת קריאה מפוזרת, קריאת רשומה ישירות מהדף | הקצאה לחיפוש 430 → 56 B; תפוקת 8 חוטים פי ~3.5 |
| 8. טרנזקציות גדולות | המאגר גדל זמנית במקום להיכשל | `CREATE INDEX` על נתונים גדולים מהמאגר עובד |

## מבנה

```
src/MiniDb.Core/                המנוע: Storage, Database, Records, Catalog, Index, Transactions, Query, Api
src/MiniDb.Cli/                 מעטפת SQL אינטראקטיבית
tests/MiniDb.Tests/             בדיקות יחידה, התאוששות ו-SQL
benchmarks/MiniDb.Benchmarks/   מדידות מול SQLite, LiteDB ו-MongoDB
```

השכבות תלויות רק כלפי מטה: `Api → Query → Index/Transactions → Storage`.

## מגבלות ידועות

- כותב אחד בכל רגע; קוראים מחכים לכותב (אין MVCC או snapshots). אין לכתוב מאותו חוט בזמן שהוא עובר על `Scan` עצל: הקריאה מחזיקה נעילה והכתיבה נכשלת ב-`LockRecursionException`.
- SQL: אין `LEFT JOIN`, `HAVING`, `NULL`, `DISTINCT`, ותת-שאילתות. `UPDATE` ו-`DELETE` דורשים `WHERE`. אין `!=`.
- JOIN רק `INNER`, עם שוויון בין שתי עמודות. הטבלה השמאלית נסרקת תמיד במלואה, ואין סידור מחדש של טבלאות.
- ב-`GROUP BY` אפשר לבחור רק עמודות מתוך קבוצת ההקבצה או אגרגטים. אין ORDER BY על אגרגט עצמו; יש למיין לפי שם עמודה שמופיעה ב-SELECT.
- אינדקס מחרוזות משווה לפי 4 התווים הראשונים בלבד. אם רוב השורות חולקות קידומת, המתכנן עובר לסריקה מלאה (מעל 1,024 התאמות).
- מחיקה משאירה חורים בדפי הנתונים; אין compaction או VACUUM.
- טרנזקציה שמשנה יותר דפים ממה שהמאגר מחזיק גורמת למאגר לגדול זמנית, עד פי 8 מהגודל שלו. מעבר לזה נזרקת `BufferPoolFullException`.
- דפים שנוספו לקובץ בטרנזקציה שבוטלה מוחזרים לרשימת הדפים הפנויים (ונשמרים בה בכותרת). אם המערכת קורסת בין הביטול להחזרה, הדפים האלה נשארים לא בשימוש עד שייבנה מחדש קובץ.
- `FsyncOnCommit=false` מאיץ commits, אבל אחרי הפסקת חשמל ייתכן שיאבדו ה-commits האחרונים. הקובץ נשאר עקבי, כי היומן נכתב לדיסק לפני כל דף.
- לא נבדק מול PostgreSQL (דורש סיסמה), ועמידות LiteDB לא אומתה.
